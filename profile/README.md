<h2>一、问题一：纯净到底指哪几项</h2>
<h3>地址层的三项</h3>
<p>第一，类型是住宅而非机房；第二，ASN 归属当地运营商；第三，近半年没有大量滥用记录。三项都能查到，查不到就别买。公开的 IP 信息库可以交叉验证，两个库结论一致才算数。</p>
<h3>行为层的两项</h3>
<p>一是历史登录行为是否单一，这条线在过去是否只服务过少量账号；二是地址是否长时间未变。这两项不能靠查询页看，只能问服务商要分配记录，或者用试跑期的日志自己观察。行为层比地址层更影响实际体验，却常常没人问。</p>

<h2>二、问题二：先拿几条合适</h2>
<p>不是越多越好，也不是一条就够。起步测试要覆盖你未来主要使用的城市与运营商，所以下限是两到三条，上限不建议超过五条。数量太少测不出差异，太多则增加观察负担。下表是常见规模的建议起始条数，可按自己的账号数微调。</p>

<h2>三、问题三：跑通的标准是什么</h2>

<h3>四条硬线</h3>
<p>一是试跑期内无断连，或断连不超过一次；二是出口地址零漂移；三是登录时没有被要求额外验证；四是连续在线八小时不掉。四条都达成，可以认定这条线跑通了。</p>
<h3>两条软线</h3>
<p>一是响应耗时稳定在可接受范围，二是同一时段多环境并行不互相拖慢。软线不达标不一定要换线，可以先优化本地带宽或错开操作时间。硬线不达标则不必优化，直接换。</p>
<h3>记录要能对比</h3>
<p>每条线每天一行记录，包括日期、断连次数、地址是否变化、验证次数、平均耗时。七天下来横向一比，哪条线好一目了然。没有记录就只剩印象，而印象往往被最近一次故障主导。</p>

<h2>四、问题四：批量下单前要补哪些材料</h2>
<h3>三份东西</h3>
<p>第一份是试跑记录，按上面的字段整理成表；第二份是账号与出口的绑定表模板，放量时直接往里填；第三份是扩容节奏说明，写清每周加多少、观察多久。前两份自己用，第三份在和服务商沟通时能省很多来回，对方知道你的节奏，更容易留出资源。</p>
<h3>把要求写进订单</h3>
<p>放量前明确三件事：能否指定城市、能否预留条数、异常时多久给替代资源。三条都落实到订单备注，比口头确认可靠。放量阶段最怕的是「线不够，先凑合用别处的」，跨城补线会破坏定位一致性。</p>

<h2>五、问题五：长期挂着怎么防中途掉线</h2>
<h3>三件事要常驻</h3>
<p>一是探测脚本，每五分钟一次，连续三次失败推送到群里；二是备用线路，同城一条，平时不用；三是变更记录，任何配置调整都写一行。三件事成本很低，但能覆盖绝大多数夜间事故。</p>
<h3>什么情况下才切备用</h3>
<p>只有确认主线故障才切：地址漂移、连续断连超过十分钟、服务商确认链路异常。切过去之后记录时间，恢复后切回，不要让两条线长期同时在线，那会产生两个出口记录。</p>
<h3>月度复核看三个数</h3>
<p>断连次数、验证次数、地址变化次数。三个数都在容忍范围内就续；某一项连续两个月超标，就换。复核周期不要拉长到一个季度，太久会让问题积累到无法归因。</p>

<h2>常见问答</h2>
<h3>试跑期用便宜的按量计费可以吗？</h3>
<p>答：可以，但要注意按量计费的线路资源池可能和包月不同。试跑的目的是验证你将来要长期用的那类资源，如果两者池子不一样，试出来的结论不能直接套用。下单前问清是否同一资源池。</p>
<h3>几条线一起跑，怎么避免互相影响？</h3>
<p>答：每条线配独立环境，操作时间错开至少十分钟，日志分开记。测试期不要用同一批账号在两条线上来回切，那样会把两条线的表现混在一起，无法判断是哪条的问题。</p>
<h3>放量时一次加多少比较稳？</h3>
<p>答：单次不超过现有量的三成到五成，加完观察一周。加量期间暂停其他变更，比如不要同时升级浏览器或调整脚本，否则出问题分不清原因。</p>
<h3>长期挂着需要每天看吗？</h3>
<p>答：不需要人工每天盯，但需要有告警。每天花两分钟看一眼告警记录和在线数即可，重点看有没有新增断连。真正需要人工判断的是连续两三天出现同类异常，那说明有趋势性问题。</p>
